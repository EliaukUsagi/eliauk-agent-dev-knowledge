# 11 实战项目方案

> 本章目标：给出 3 个**企业级**练手项目的完整方案：架构、多技术栈选型、数据模型、里程碑与**可量化的验收标准**。每个项目都对应企业中真实高频的需求，做完可以直接作为作品集或内部落地的原型。

---

## 一、项目选择

| 项目 | 对应企业需求 | 核心能力 | 覆盖章节 | 难度 | 周期 |
|---|---|---|---|---|---|
| **项目一：带权限的企业知识库** | 制度问答、产品手册、技术文档助手 | 企业 RAG、权限、引用、评测 | 04 / 07 / 09 / 10 | ⭐⭐⭐ | 2 周 |
| **项目二：业务系统内嵌 Copilot** | 给已有后台加 AI 助手 | 工具调用、审批、MCP、生成式 UI | 04 / 05 / 06 / 10 | ⭐⭐⭐ | 1.5 周 |
| **项目三：企业 AI 网关 + 用量看板** | AI 平台团队基础设施 | 网关、限流计费、可观测 | 03 / 09 / 10 | ⭐⭐ | 1 周 |

> 🎯 **建议顺序**：先做**项目一**（企业价值最高，覆盖 RAG 全链路），再做**项目二**（Agent、MCP、审批），最后做**项目三**，把前两个项目的模型调用都接到自己的网关上，形成完整体系。

### 1.1 技术栈方案

三个项目都可以用不同的技术栈实现。**为了拓宽视野，建议三个项目至少使用两种不同的主力语言**，并让它们通过协议（OpenAI 兼容 API、MCP、A2A）互相连接：

| 层 | Python 主线 | TypeScript 主线 | Java 主线 |
|---|---|---|---|
| Agent / 编排 | LangGraph | Vercel AI SDK 7 | Spring AI Alibaba / LangChain4j |
| API 服务 | FastAPI | Next.js Route Handler / Hono | Spring Boot |
| 前端交互 | 任一前端 + AG-UI（如 CopilotKit） | AI SDK UI（`useChat`） | 任一前端 + AG-UI |
| 文档解析 | MinerU / Docling（原生） | 调用 Python 解析服务 | 调用 Python 解析服务 |
| MCP Server | 官方 Python SDK v2 | 官方 TS SDK v2 | Spring AI `@McpTool` |
| 任务队列 | Celery / Arq | BullMQ | Spring Batch / MQ |
| 网关（项目三） | 基于 LiteLLM 二次开发 | Hono 自研 | — （Go 自研或 Higress 也是好选择） |

公共基础设施：PostgreSQL（pgvector）、Redis、MinIO、Langfuse 或 Phoenix，用一份 `docker-compose.yml` 统一启动。

推荐的仓库结构（多语言并存）：

```text
ai-lab/
├── services/
│   ├── kb/                     # 项目一：知识库服务（如 Python + FastAPI + LangGraph）
│   ├── ingest/                 # 项目一：文档解析与入库 Worker（Python）
│   ├── copilot/                # 项目二：Copilot Agent 服务（如 TS + AI SDK）
│   └── gateway/                # 项目三：AI 网关
├── mcp-servers/
│   └── orders/                 # 项目二：订单 MCP Server（任一语言）
├── web/                        # 前端：对话 UI、业务后台、用量看板
├── evals/                      # 评测集与评估器（与语言无关的数据 + 评测脚本）
└── infra/docker-compose.yml    # PG（pgvector）、Redis、MinIO、Langfuse
```

## 二、项目一：带权限的企业知识库问答

### 2.1 需求

**背景**：公司制度、产品手册、技术文档分散在网盘和 Wiki 中，员工找不到、看不懂；不同部门的文档权限不同。

**目标**：
- 员工用自然语言提问，得到**带引用**的准确回答
- 员工**只能检索到有权限的文档**
- 文档更新、删除、权限变更后自动同步

**非目标**（第一版不做）：多模态（图片内容理解）、跨语言、GraphRAG

### 2.2 架构

```mermaid
graph TB
    subgraph Web["kb 服务（Web 前端 + API）"]
        UI[流式对话 UI<br/>引用角标]
        ADM[管理后台<br/>文档 / 权限 / 评测]
        API["/api/chat"]
    end
    subgraph Ingest["入库服务（Python Worker）"]
        Q[(Redis 队列)]
        P[解析：MinIO 取文件 → MinerU / Docling]
        CH[结构化切片 + 标题路径增强]
        EM[向量化]
    end
    DB[(PostgreSQL<br/>pgvector + 全文索引 + ACL)]
    LF[Langfuse]
    UI --> API
    API -->|改写 → 混合检索 + ACL → Rerank → 生成| DB
    ADM -->|上传 / 权限变更| Q --> P --> CH --> EM --> DB
    API -.trace.-> LF
```

### 2.3 技术选型

| 环节 | 选型 | 理由 |
|---|---|---|
| 检索与生成服务 | Python：FastAPI + LangGraph（或按 1.1 节选择其他主线） | RAG 生态最完整；LangGraph 便于实现 Agentic RAG 进阶 |
| 前端 | 任一 Web 框架，经 SSE / AG-UI 对接 | 流式、引用、进度推送（[04 章](./04-AI交互层-流式协议与生成式UI.md)） |
| 文档解析 | MinerU 或 Docling | 表格与版面效果好 |
| 存储 | PostgreSQL + pgvector + 中文全文检索 | 一个数据库同时解决向量、全文、ACL、业务数据 |
| Embedding / Rerank | BGE-M3 + BGE-Reranker 等（本地或云 API） | 中文效果好，可私有化（[07 章 4.4](./07-企业级RAG落地.md#44-embedding-与-rerank-模型选型)） |
| 队列 | Redis + Celery / Arq | 支持重试与并发控制 |
| 评测 | Ragas + 自定义规则评估器 | 检索与生成指标 |
| 可观测 | Langfuse 或 Phoenix（私有化） | Trace + 评测 + Prompt 管理 |

### 2.4 核心数据模型

```sql
-- 用户与组（模拟 IdP，实际项目对接公司 SSO）
CREATE TABLE users  (id text PRIMARY KEY, name text, tenant_id text);
CREATE TABLE groups (id text PRIMARY KEY, name text, parent_id text);
CREATE TABLE user_groups (user_id text, group_id text, PRIMARY KEY (user_id, group_id));

-- 文档
CREATE TABLE documents (
  id text PRIMARY KEY, tenant_id text, title text, source_url text,
  doc_type text, content_hash text, status text,   -- pending / indexing / ready / failed
  acl_principals text[] NOT NULL, updated_at timestamptz
);

-- 块：冗余存储 ACL，避免检索时联表
CREATE TABLE chunks (
  id text PRIMARY KEY, tenant_id text, doc_id text REFERENCES documents ON DELETE CASCADE,
  content text, heading_path text[], page int,
  embedding vector(1024), tsv tsvector, principals text[] NOT NULL
);

-- 对话与反馈
CREATE TABLE chats    (id text PRIMARY KEY, user_id text, messages jsonb, updated_at timestamptz);
CREATE TABLE feedback (id serial, chat_id text, message_id text, rating int, comment text, trace_id text);
```

### 2.5 里程碑

| 里程碑 | 内容 | 产出 |
|---|---|---|
| **M1 跑通（2~3 天）** | 上传 PDF → 解析 → 切片 → pgvector；纯向量检索 + 流式回答 | 能问答的最小版本 |
| **M2 准确（3~4 天）** | 标题路径增强、混合检索 + RRF + Rerank、多轮查询改写、引用与校验、拒答阈值 | 构建 50 条评测集，记录基线 |
| **M3 安全（2~3 天）** | 用户 / 组 / ACL、检索前置过滤、权限变更同步、删除同步、越权测试 | 越权召回率 = 0 |
| **M4 可运营（2 天）** | Langfuse trace、点赞点踩、badcase 入评测集、评测脚本进 CI | 评测报告 + 看板 |

### 2.6 验收标准

| 指标 | 目标 |
|---|---|
| 检索 Recall@5（评测集） | ≥ 85% |
| 回答忠实度（LLM-as-Judge + 人工抽检） | ≥ 90% |
| 应拒答问题的拒答率 | ≥ 90% |
| **越权召回率**（低权限账号测试） | **= 0** |
| 首 token 延迟 P95 | ≤ 3 秒 |
| 文档权限变更生效时间 | ≤ 5 分钟 |

### 2.7 进阶挑战

- 实现**蓝绿索引**：更换 Embedding 模型时不停服重建
- 加入 **Agentic RAG**：复杂问题由 Agent 多轮检索，对比评测集上的收益与成本
- 对接飞书 / 钉钉 / Confluence 作为数据源，实现增量同步

## 三、项目二：业务系统内嵌 Copilot

### 3.1 需求

**背景**：已有一个订单管理后台（可以自己搭一个简化版），运营人员每天要做大量筛选、查询、批量操作。

**目标**：
- 在后台右侧嵌入 AI 助手，运营用自然语言完成"查一下上周华东区退款超过 500 元的订单"之类的操作
- AI 能**操作页面**（修改筛选条件、打开详情）和**调用业务接口**（查询、退款、备注）
- 高风险操作必须审批
- 订单工具同时以 **MCP Server** 形式暴露，可以在 Claude Code 等客户端中使用

### 3.2 架构

```mermaid
graph TB
    subgraph Admin["业务后台 + Copilot"]
        PG[订单列表页<br/>筛选 / 表格 / 详情]
        CP[Copilot 面板]
        FT[前端工具<br/>setFilters / openOrder]
        R["Copilot Agent 服务"]
    end
    MCP[orders MCP Server<br/>Streamable HTTP + JWT 鉴权]
    BIZ[(订单业务 API / DB)]
    EXT[Claude Code 等<br/>外部 MCP 客户端]

    PG -->|当前视图上下文| CP
    CP --> R
    R -->|工具调用回到前端| FT --> PG
    R -->|MCP 客户端| MCP --> BIZ
    EXT --> MCP
```

### 3.3 工具设计

| 工具 | 位置 | 风险级别 | 审批策略 |
|---|---|---|---|
| `setFilters` | 前端 | L0 | 自动 |
| `openOrderDetail` | 前端 | L0 | 自动 |
| `search_orders` | MCP | L1 | 自动 + 审计 |
| `get_order_overview` | MCP | L1 | 自动 + 审计 |
| `add_order_note` | MCP | L2 | 自动 + 审计 |
| `refund_order` | MCP | L4 | **金额 ≤ 100 自动；否则审批；单日累计额度上限** |
| `batch_update_status` | MCP | L3 | **强制审批，展示受影响订单列表** |

### 3.4 关键实现点

两条可选实现路线：

| 路线 | Agent 服务 | 前端 | 前端工具 / 共享状态 |
|---|---|---|---|
| **全栈 TS** | AI SDK 7 `ToolLoopAgent` | `useChat` | 不定义 `execute` 的工具，前端执行后用 `addToolOutput` 回传 |
| **Python / Java 后端 + AG-UI** | LangGraph / Spring AI Alibaba 等 | CopilotKit 或自研 AG-UI 客户端 | AG-UI 的 Frontend Tools 与 `STATE_DELTA` |

**① 页面上下文按需提供**

```jsonc
// 只传当前视图的关键状态，详细数据让模型通过工具查询
{
  "page": "orders/list",
  "filters": { "region": "华东", "status": "refunded" },
  "selectedOrderIds": ["O-1024", "O-1031"],
  "totalInView": 312
}
```

**② 前端工具**

服务端只声明 `setFilters` 的 schema，不负责执行。工具调用到达前端后由页面执行，执行结果回传给 Agent（实现方式见上表）。

**③ 工具结果渲染为业务组件**

`search_orders` 的结果直接渲染为可点击的订单表格组件，而不是让模型复述。

**④ MCP Server 鉴权**

MCP Server 校验 JWT 的签名、`aud`、`scope`，以 token 中的用户身份调用业务 API，**不透传 token**（[05 章第七节](./05-MCP与Agent互操作协议.md#七鉴权企业落地的核心重点)）。**用与 Agent 服务不同的语言实现 MCP Server**，体会协议带来的解耦。

### 3.5 里程碑

| 里程碑 | 内容 |
|---|---|
| **M1（2 天）** | 搭建订单后台（mock 数据）+ Copilot 面板；本地工具 `search_orders`，结果渲染为表格 |
| **M2（2 天）** | 前端工具 `setFilters` / `openOrderDetail`；页面上下文注入；路由到便宜模型做意图分类 |
| **M3（2 天）** | 抽出 orders MCP Server（官方 SDK，Streamable HTTP + JWT），Copilot 改为通过 MCP 客户端调用；在 Claude Code 中接入验证 |
| **M4（2 天）** | 退款与批量操作的审批流、额度上限、幂等键；审计日志；红队测试（订单备注中的间接注入） |

### 3.6 验收标准

| 指标 | 目标 |
|---|---|
| 30 条典型指令的任务完成率 | ≥ 85% |
| L3 / L4 操作未经审批即执行的次数 | **= 0** |
| 订单备注间接注入测试 | 不触发任何写操作 |
| 重放同一审批请求 | 不产生重复退款（幂等） |
| 同一 MCP Server 在 Claude Code 中可用 | ✅ |

### 3.7 进阶挑战

- 把退款审批改为**持久化执行**（LangGraph Checkpointer、Temporal 或 AI SDK `WorkflowAgent`），支持主管异步审批（数小时后恢复执行）
- 用 A2UI 或 MCP Apps 让 `get_order_overview` 返回可交互的订单卡片
- 加入长期记忆：记住运营人员的常用筛选习惯
- 把"财务对账"做成另一个团队的独立 Agent，Copilot 通过 **A2A** 委托对账任务

## 四、项目三：企业 AI 网关 + 用量看板

### 4.1 需求

**背景**：多个团队各自对接模型厂商，密钥散落、费用不透明、无法统一限流和降级。

**目标**：
- 提供 OpenAI 兼容接口，业务方只改 `baseURL` 即可接入
- 虚拟 Key、按团队配额、RPM / TPM 限流
- 多渠道负载均衡与自动降级
- 用量与费用看板

### 4.2 架构

```mermaid
graph LR
    C[业务应用<br/>项目一 / 项目二] -->|OpenAI 兼容协议<br/>虚拟 Key| G
    subgraph G["gateway"]
        A[鉴权<br/>虚拟 Key → 团队]
        L[限流<br/>Redis 令牌桶 RPM / TPM]
        RT[路由<br/>模型 → 渠道列表]
        F[重试 / 降级]
        M[计量<br/>流式 usage 解析]
    end
    G --> P1[厂商 A] & P2[厂商 B] & P3[私有化 vLLM]
    M --> DB[(PostgreSQL<br/>用量明细)]
    DB --> D[看板<br/>Web + 图表]
```

### 4.3 路线选择

| 路线 | 做法 | 适合 |
|---|---|---|
| **A. 基于 LiteLLM / New API / Higress 二次开发** | 部署开源网关，补充企业 SSO、看板定制 | 想快速落地 |
| **B. 自研（推荐用于学习）** | 用 Go（高并发网关的主流语言）、Python 或 TS 实现核心链路，参考开源方案的设计 | 想吃透网关原理 |

### 4.4 关键实现点

- **流式透传**：边收边转发，不缓冲；在流结束时解析 usage 并计费（[09 章 5.3](./09-LLMOps-可观测评测与AI网关.md#53-自研网关的关键实现点)）
- **TPM 预扣 + 结算**：请求前按 `输入 token + max_tokens` 预扣，结束后按实际用量多退少补
- **降级判定**：只对 429、5xx、超时降级，4xx 参数错误不降级
- **客户端断开**：上游请求同步中止，按已输出内容计费
- **密钥安全**：厂商 Key 加密存储，日志中不出现任何 Key

### 4.5 里程碑

| 里程碑 | 内容 |
|---|---|
| **M1（2 天）** | `/v1/chat/completions` 透传（含流式）；虚拟 Key 鉴权；用量记录 |
| **M2（2 天）** | Redis 限流（RPM / TPM）；团队配额；多渠道负载均衡与降级 |
| **M3（2 天）** | 看板：按团队 / 模型 / 天的 token 与费用；TTFT、错误率；预算告警 |
| **M4（1 天）** | 项目一、项目二的模型调用全部切换到网关；按数据密级路由（[10 章 7.2](./10-安全权限与上线清单.md#72-按数据密级路由模型)） |

### 4.6 验收标准

| 指标 | 目标 |
|---|---|
| 网关引入的额外 TTFT | ≤ 50 ms |
| 流式透传 | 无缓冲，逐 chunk 到达 |
| 计量误差（与厂商账单对比） | ≤ 1% |
| 主渠道故障时 | 自动切换，业务请求成功率 ≥ 99% |
| 超出 TPM | 返回 429 和 `Retry-After` |

## 五、作品集与面试表达

做完项目后，按下面的结构整理成作品说明，这也是面试中讲项目的框架：

```text
1. 业务问题：解决什么问题，为什么现有方案不行
2. 架构决策：为什么选平台 / 框架 / 自研；为什么是 Workflow 还是 Agent
3. 关键难点：选 1~2 个讲透（如权限过滤召回不足、流式计量、审批防篡改）
4. 量化结果：评测指标基线 → 优化后（Recall@5 从 62% 提升到 88%）
5. 治理设计：权限、安全、成本、可观测分别怎么做
6. 反思：哪些设计做错了，下一版会怎么改
```

> 🎯 **落地要点**：能体现"企业级"的不是功能有多少，而是**第 4 点和第 5 点**：有评测数据支撑效果，有治理设计支撑上线。

## 本章小结

- 三个项目分别对应企业 AI 落地最高频的三类需求：**知识库、业务 Copilot、AI 网关**
- 每个项目都按"**跑通 → 准确 → 安全 → 可运营**"四个里程碑推进
- 验收标准必须**可量化**，安全类指标（越权召回、未审批执行）必须为 0
- 三个项目建议使用**至少两种主力语言**，通过 OpenAI 兼容 API、MCP、A2A 串成一个完整的企业 AI 体系
